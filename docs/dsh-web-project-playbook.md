# 通用 Web 项目开发规范（DSH 可直接执行版）

> 版本：1.0  
> 用途：新建立项、需求评审、让 DSH 接管开发、发布前验收。  
> 使用方式：复制到新项目根目录或 `docs/` 下，填写所有 `<...>` 占位符；不适用的章节写 N/A，不要静默删除约束。  
> 适用对象：多用户、带登录、有明确业务状态、需要长期运维的 Web 应用。纯展示站可删掉数据/权限/发布章节。

---

## 0. 给 DSH 的执行约定

这一节优先级最高，和具体业务无关。

### 0.1 命令执行

- 执行 shell 命令优先使用 `ops_bash`，不要因为个人习惯改用其他 shell 工具。
- 不要用 shell 命令替代文件读取；读文件用 `read`，搜索用 `grep` / `glob`。
- 修改文件优先 `edit` / `write`；批量生成或格式化可以跑命令，但最终 diff 必须人工复核。
- 命令失败先读错误和退出码，不要立刻换一种写法绕过。只有确认是环境限制时，才换路径并说明原因。
- 删除、移动、覆盖、重置数据库、清理 Docker 卷之前，先确认绝对路径和影响范围。
- 不要执行 `git reset --hard`、`git clean -fd`、`docker compose down -v` 这类不可逆命令，除非用户明确要求并确认目标。
- 不要请求沙箱提权；当前环境不允许的路径，换合法路径或报告阻塞。

### 0.2 Git 与网络

- Git 网络不通时，优先完成本地提交和本地 tag，保证工作不丢。
- 不要在 push 失败后反复重试 DNS、代理、hosts、SSH 端口等网络技巧；记录失败阶段，报告“已本地提交、未推送”。
- 不要为了推送成功改写历史、强推、删除远端 tag，除非用户明确要求。
- 没有实际验证远端结果前，不要声称“已推送”“已发布”“Release 已创建”。
- 本地提交信息要能独立说明改动；不要把所有改动堆成一个“update”。
- 发布 tag 必须指向已经验证过的提交。

推荐流程：

```bash
git status
git add -A
git commit -m "feat: <一句话说明>"

# 网络可用时
git push origin main
git push origin <tag>

# 网络不可用时
# 保留本地 commit/tag，报告：
# - commit hash
# - tag 名
# - 卡在哪一步
# - 远端当前状态未知
```

### 0.3 工作方式

1. 先读仓库约定和现有实现，再写代码。
2. 先做最小端到端闭环，再补全分支和边界。
3. 修根因，不在调用方层层打补丁。
4. 不为不存在的需求增加抽象、兼容层、开关、插件点。
5. 新逻辑必须带测试；修 bug 先写能复现的失败测试。
6. 改动完成后检查失败路径、清理路径、重复执行、所有调用方。
7. 交付前跑完整门禁，并用生产构建实际启动验证。
8. 交付说明写清楚：改了什么、为什么、怎么验证、如何回滚。

| 项                | 值                                |
| ----------------- | --------------------------------- |
| 项目名            | `<PROJECT_NAME>`                  |
| 一句话定位        | `<为谁解决什么问题>`              |
| 核心用户          | `<角色 A、角色 B>`                |
| 部署形态          | `<单机 Docker / 云托管 / 纯静态>` |
| 访问地址          | `<https://...>`                   |
| 数据敏感级别      | `<公开 / 内部 / 含个人信息>`      |
| 是否需要移动端    | `<是 / 否>`                       |
| 是否需要离线/内网 | `<是 / 否>`                       |

### 1.2 核心闭环

只写一条最重要的主流程，必须能端到端跑通：

```text
<角色> 登录

```

**本期做：**

- `<功能 1>`

**本期不做：**

- `<明确排除的功能>`
- `<明确不支持的规模/终端>`

> “不做”必须写出来，否则开发过程中一定会被临时需求带偏。

## 2. 角色、权限与状态

### 2.1 角色权限矩阵

| 角色       | 数据范围            | 可执行操作 | 明确禁止 |
| ---------- | ------------------- | ---------- | -------- |
| 超级管理员 | 全局                | `<...>`    | `<...>`  |
| 管理员     | 本组织/本团队       | `<...>`    | 跨组织   |
| 普通用户   | 本人/本团队授权范围 | `<...>`    | 管理配置 |
| 只读用户   | 授权范围            | 查看/导出  | 写入     |

要求：

- 每个写操作都必须能落到某个角色的权限判断。
- 前端隐藏按钮只是体验，服务端必须重新校验。
- 越权访问统一返回 NOT_FOUND，不泄露资源是否存在。
- 跨组织/跨团队查询必须在 SQL 层带范围条件，不能查出来再过滤。

### 2.2 状态机

核心对象必须画状态机，并写明：

- 初始状态
- 允许的转换
- 每个转换的触发角色
- 失败条件
- 终态
- 是否允许撤销/重开

```text
<待处理> → <已接收> → <已完成>
    │           │
    │           └→ <异常> → <已处理>
    └→ <已取消>
```

要求：

- 状态只由服务端事务修改。
- 不允许前端直接传“目标状态”绕过业务检查。
- 每个状态至少有：正常、无权限、重复操作、非法转换四种测试。
- 终态记录默认不允许再改核心字段。

## 3. 设计指令

### 3.1 页面清单

每个页面写清楚：

| 页面    | 路径     | 角色    | 主操作  | 空状态  | 失败状态 |
| ------- | -------- | ------- | ------- | ------- | -------- |
| `<...>` | `</...>` | `<...>` | `<...>` | `<...>` | `<...>`  |

### 3.2 页面必须具备的状态

- 加载中
- 空数据
- 请求失败 + 重试
- 无权限
- 已归档/已停用/已完成等终态
- 提交中/防重复提交
- 字段级错误
- 成功反馈
- 危险操作二次确认

不要只设计“有数据且一切正常”的页面。

### 3.3 交互原则

- 一屏一个主操作。
- 主按钮、次按钮、危险按钮层级清楚。
- 不可逆操作说明后果，不只写“确认删除”。
- 失败提示说明下一步，不只抛错误码。
- 长表单分块，错误定位到字段。
- 弹窗内容过长时内部滚动，底部操作区固定。
- 移动端触控目标不小于 44px。
- 底部操作区考虑安全区。
- 320–768px 全页面无横向溢出。

### 3.4 视觉系统

至少定义：

- 颜色令牌：背景、卡片、边框、主色、成功、警告、危险、弱化文字。
- 字体层级：页面标题、区块标题、正文、辅助文字。
- 间距刻度：4 / 8 / 12 / 16 / 24 / 32。
- 圆角、阴影、焦点环。
- 深色模式。
- 组件变体：按钮、输入、选择器、弹窗、标签、空状态、错误状态。

应用代码优先使用组件 variant，不要到处写一次性颜色和间距。

### 3.5 文案

- 用业务语言，不用技术语言。
- 说清“会发生什么”。
- 空状态给出下一步。
- 权限不足说明找谁。
- 危险操作说明不可逆性和历史影响。

### 3.6 可访问性

- 表单控件必须有 label。
- 图标按钮必须有 `aria-label`。
- 键盘可操作，焦点可见。
- 状态不能只靠颜色区分。
- 对比度满足基本可读性。
- 弹窗打开后焦点进入弹窗，关闭后回到触发点。

## 4. 技术基线

以下为默认参考栈，可按团队替换；替换的是工具，不是边界原则。

| 层     | 默认选择                           | 关键要求                   |
| ------ | ---------------------------------- | -------------------------- |
| 运行时 | Node 24                            | 开发、构建、生产版本一致   |
| 前端   | React 19 + TanStack Router / Query | 路由与数据请求分层         |
| 样式   | Tailwind + shadcn/Base UI          | 设计令牌 + 组件变体        |
| 后端   | Hono                               | 轻量、同源部署方便         |
| API    | oRPC + Zod                         | 端到端类型安全，无 codegen |
| 数据库 | SQLite + Drizzle                   | 事务、迁移、WAL            |
| 认证   | Better Auth 或同类                 | Cookie 会话、服务端中间件  |
| 测试   | Vitest + Playwright                | 集成 + 端到端              |
| 部署   | Docker + GHCR                      | 镜像不可变、可回滚         |

### 4.1 命令约定

新项目必须固定以下命令，DSH 不得自行猜测：

| 用途           | 命令               |
| -------------- | ------------------ |
| 安装           | `<pnpm install>`   |
| 开发           | `<pnpm dev>`       |
| 格式/Lint/类型 | `<pnpm check>`     |
| 单元/集成测试  | `<pnpm test>`      |
| E2E            | `<pnpm test:e2e>`  |
| 构建           | `<pnpm build>`     |
| 完整门禁       | `<pnpm run ready>` |

若采用 Vite+，参考值为：`vp check`、`vp test`、`vp run test:e2e`、`vp run build`、`vp run ready`。

### 4.2 硬约束

1. 单仓库、边界清晰：Web、Server、API、DB、Auth、UI 各自负责一层。
2. 单源部署：开发用代理，生产由后端服务 SPA；浏览器只看到一个 Origin，Cookie 第一方，不配 CORS。
3. 认证地址必须精确：`APP_URL` / `BETTER_AUTH_URL` 必须等于浏览器实际访问地址，协议、域名、端口、结尾都不能错。
4. API 不直接返回数据库行：统一映射 DTO，隐藏内部字段，补全派生字段。
5. 错误码统一：`BAD_REQUEST`、`UNAUTHORIZED`、`FORBIDDEN`、`NOT_FOUND`、`CONFLICT`。
6. 环境变量集中校验：启动时检查必填项，缺失直接失败。
7. 服务端产物必须真实启动验证：测试通过不等于 bundle 能跑。

## 5. 架构要求

### 5.1 目录边界

```text
apps/web          React SPA：路由、页面、组件、请求
apps/server       Hono：认证、API、静态资源、启动
packages/api      API 路由、鉴权、DTO、集成测试
packages/db       Schema、迁移、数据库连接
packages/auth     认证配置、会话类型
packages/ui       通用 UI 组件
packages/config   TypeScript / Lint 等共享配置
```

### 5.2 请求链路

```text
浏览器
  → Web 页面 / TanStack Query
  → 类型安全 API 客户端
  → 后端认证中间件
  → API procedure
  → Drizzle
  → SQLite
```

- 开发环境代理 `/api`、`/rpc` 到后端。
- 生产环境由后端直接服务前端构建产物。
- 不引入第二套 API 网关，除非有明确外部约束。

### 5.3 环境变量

- 所有变量在 `env` schema 中声明。
- 提供 `.env.example`，写安全示例值。
- 真实 `.env` 不进 Git。
- 前端不持有任何密钥。
- 启动时校验，缺失或格式错误直接退出。

### 5.4 构建与运行

- 构建产物只包含运行所需文件。
- 生产镜像不以 root 运行。
- 数据库、上传文件放在持久化卷。
- 健康检查不依赖镜像里可能不存在的工具，优先用 Node 自带 `fetch`。
- 生产启动失败必须能从日志看出是环境、迁移还是端口问题。

## 6. 数据要求

### 6.1 Schema

- 主键统一。
- 时间字段统一：`createdAt` / `updatedAt`。
- 状态用 CHECK 约束。
- 唯一性用唯一索引。
- 外键明确级联/限制。
- 非空、长度、范围同时写 Zod 和数据库约束。
- 金额、库存、数量使用不会丢精度的类型。

### 6.2 事务

以下操作必须原子：

- 扣库存 + 写流水 + 写明细
- 调拨：扣源库存 + 增目标库存 + 双边流水
- 审批：改状态 + 恢复库存 + 写流水
- 删除主记录 + 清理关联资源
- 批量导入：整批成功或整批失败

事务内失败整体回滚，不能留下半条数据。

### 6.3 实时数据与快照

必须区分：

- 实时主数据：当前名称、规格、单位、库存、状态。
- 历史快照：已提交记录中保存的名称、数量、操作人。

规则：

- 已完成记录默认冻结快照。
- 未完成草稿可以同步最新主数据。
- 同步范围要明确，例如只同步名称/规格/单位，不动数量和已核对结果。
- 一旦进入终态，不再随主数据变化。

### 6.4 删除策略

至少区分：

- 停用/归档：保留历史，禁止新业务引用。
- 普通删除：仅允许无业务引用的数据。
- 彻底删除：明确清理哪些关联数据，说明不可恢复。
- 历史保护：有账目、审批、交接快照的数据，即使彻底删除也应拒绝或要求特殊审批。

删除前查引用，删除时同一事务清理关联表。

### 6.5 审计与迁移

- 核心记录保存操作人 ID + 姓名快照。
- 账号改名/停用后历史仍可读。
- 已提交的迁移不再修改。
- 每次 schema 变更生成新迁移。
- 发布前在空库和旧库上都跑一遍迁移。

### 6.6 查询与性能

- 列表分页，不一次拉全量。
- 列表不加载大字段（图片二进制、长文本）。
- 图片上传后服务端压缩、裁剪、限制大小和类型。
- 高频查询建索引：外键、状态、日期、唯一键。
- 避免 N+1；需要名称时批量查映射。
- 统计查询与列表查询分开。

## 7. API 要求

### 7.1 过程设计

- 一个过程一个职责：列表、详情、创建、更新、删除、审批分开。
- 输入用 Zod 在边界校验，内部信任已校验类型。
- 输出统一 DTO，不直接返回 ORM 行。
- 错误码和错误信息统一。
- 分页、排序、时间范围必须有上限。
- 批量接口必须限制条数。

### 7.2 权限

- 每个读写过程都按用户/组织/资源范围过滤。
- 每个新过程至少测试：匿名、越权、正常、边界、冲突。
- 越权返回 NOT_FOUND。
- 不允许“先查全量再在内存里过滤”。

### 7.3 幂等与并发

- 重复提交、重复审批、重复入库要有唯一约束或状态检查。
- 并发扣减用条件更新：`UPDATE ... WHERE id = ? AND stock >= ?`。
- 影响行数为 0 时回滚并返回 CONFLICT。
- 文件上传校验 MIME、大小、解码结果；服务端重新编码。

### 7.4 文件与静态资源

- 上传目录不可由用户控制。
- 文件名使用随机 ID，不使用原始文件名做路径。
- 读取文件必须鉴权并校验归属。
- 静态资源带缓存版本号。
- 不在 API 中返回本地绝对路径。

## 8. 前端要求

### 8.1 路由与数据

- 路由负责页面和权限入口。
- Query 负责服务端状态，不把服务端数据复制进全局 store。
- 登录态从路由 context 或统一 hook 读取。
- 页面隐藏是 UX，不是安全边界。
- 退出登录清空查询缓存。

### 8.2 表单

- 字段有 label、错误提示、最大长度。
- 提交中禁用重复提交。
- 失败保留用户输入。
- 危险操作二次确认。
- 成功后刷新相关查询，不只弹 toast。
- 日期、时间、数量做格式化和边界校验。

### 8.3 列表与详情

- 加载、空、错误、无权限状态齐全。
- 分页/筛选条件写进 URL，可刷新恢复。
- 行操作菜单层级清楚，危险操作单独样式。
- 关键字段缺失显示占位，不显示 `undefined`。
- 长文本换行，不撑破布局。

### 8.4 弹窗

- 移动端最大高度受视口限制。
- 内容滚动，底部操作固定。
- 关闭前如有未保存修改，提示确认。
- 打开后焦点进入弹窗。
- 同一页面多个弹窗用独立状态，避免串数据。

### 8.5 导航

- 导航按角色显示，但服务端仍校验。
- 同一功能只保留一个入口，避免重复导航。
- 当前页高亮。
- 移动端导航可展开、可关闭。
- 外链/内链行为一致。

## 9. 测试要求

### 9.1 分层

| 层   | 测什么                                    | 不测什么     |
| ---- | ----------------------------------------- | ------------ |
| E2E  | 核心用户旅程、权限、跨页面闭环            | 每个表单分支 |
| 集成 | 每个 API 的校验、权限、状态、事务、不变量 | 页面样式     |
| 单元 | 计算、解析、状态机、权限矩阵等密集逻辑    | 简单 CRUD    |

### 9.2 原则

- 期望值来自需求、验收标准、公开契约，不来自实现。
- 用真实数据库、真实迁移、真实会话。
- 每个测试文件独立数据库，避免互相污染。
- 不 mock 自己负责的数据库和认证。
- E2E 用真实浏览器、真实 API。
- 修 bug 先写失败测试。
- 测试失败先修代码，不先改断言。
- 只有业务规则确实变化时才调整预期，并在说明中写清楚。

### 9.3 门禁

发布前固定执行：

```text
格式 → Lint → 类型检查 → 未使用代码检查 → 单元/集成 → E2E → 构建
```

同时必须做一次生产构建产物启动验证：

- 进程能启动
- 健康检查 200
- 登录成功

## 10. 发布与运维要求

这一节是交付闭环，不能省略。

### 10.1 仓库必需文件

```text
.github/workflows/release.yml
Dockerfile
deploy/docker-compose.release.yml
deploy/env.release.example
scripts/ops.sh
docs/release-and-ops.md
docs/deployment-1panel.md
CHANGELOG.md
```

### 10.2 GitHub Actions

必须满足：

- 只有 tag 触发发布，main 只跑 CI。
- 质量门禁不通过不构建镜像。
- 镜像推送 GHCR，生产固定版本，不依赖 latest。
- Release 上传可部署资产，不只放源码。
- 生成 `checksums.txt`。
- 支持手动重跑，但必须指定已存在 tag。
- 权限包含 `contents: write`、`packages: write`。

发布链路：

```text
tag → 质量门禁 → 构建/推送镜像 → 组装资产 → 创建 Release → 上传文件
```

### 10.3 Dockerfile

- 多阶段构建。
- 构建阶段装依赖并编译。
- 运行阶段只保留 Node、构建产物、迁移文件。
- 非 root 运行。
- 数据目录固定挂载。
- 健康检查不依赖 curl。
- 不在镜像中放 `.env`、密钥、测试数据。

### 10.4 生产 Compose

- 不写 `build:`，只拉镜像。
- `migrate` 服务先执行，成功后 `app` 启动。
- 数据卷独立，禁止 `down -v`。
- 端口只映射内网，外部走反向代理。
- 日志限制大小。
- 环境变量缺失时启动失败，不使用危险默认值。

### 10.5 一键运维脚本

`ops.sh` 至少支持：

| 命令          | 作用                                       |
| ------------- | ------------------------------------------ |
| install       | 生成配置、拉镜像、迁移、启动、健康检查     |
| upgrade [tag] | 升级前备份、更新镜像、迁移、启动、健康检查 |
| rollback      | 回滚到上一次升级前配置                     |
| status        | 容器状态、健康检查、当前镜像               |
| logs          | 跟踪应用日志                               |
| backup        | 在线备份数据库和配置                       |
| restore       | 恢复数据库，恢复前二次确认                 |
| restart       | 重启并等待健康检查                         |
| doctor        | 检查 Docker/Compose/配置                   |
| uninstall     | 移除容器，数据卷单独确认                   |

脚本硬性要求：

- `set -Eeuo pipefail`。
- 安装目录可覆盖。
- 已有 `.env` 复用，不覆盖密钥。
- 新配置权限 `600`。
- 升级前备份。
- 迁移失败立即停止。
- 健康检查超时打印回滚命令。
- 永远不自动删数据卷。

### 10.6 Release 资产

至少包含：

```text
app-ops.sh
docker-compose.yml
env.example
DEPLOY.md
1PANEL.md
app-deploy-<tag>.tar.gz
checksums.txt
```

发布时把脚本默认镜像 tag 固定为当前版本，避免 latest 漂移。

### 10.7 详细 md 文档

`DEPLOY.md` 必须写：

1. 架构图
2. 前置条件
3. 一键安装
4. 环境变量表
5. 反向代理 / HTTPS
6. 初始化
7. 日常运维
8. 升级与回滚
9. 备份与恢复
10. 安全说明
11. 常见故障
12. 验收清单

文档必须写实际目录、实际端口、实际镜像名、实际健康检查地址，不能只写“参考配置”。

### 10.8 发布验收

- [ ] tag 能触发 Actions
- [ ] 质量门禁通过
- [ ] 镜像推送 GHCR
- [ ] Release 有完整资产和 checksums
- [ ] 新服务器一键安装成功
- [ ] 旧版本升级成功
- [ ] 升级失败能回滚
- [ ] 备份能生成，恢复能成功
- [ ] 反向代理 + HTTPS 后登录正常
- [ ] README 首屏有一键安装命令

## 11. DSH 交付流程

1. 阅读本文件和仓库现有约定。
2. 输出实施计划：角色/状态、数据模型、API、页面、测试、发布影响。
3. 做最小端到端闭环。
4. 补数据约束、事务、权限。
5. 补 UI 状态、移动端、可访问性。
6. 补测试：集成 + E2E。
7. 跑完整门禁。
8. 用生产构建实际启动验证。
9. 更新版本号、CHANGELOG、部署文档。
10. 本地提交；网络可用时推送 tag。
11. 网络不可用时保留本地 commit/tag，报告未推送。
12. 输出交付说明：改动、验证、风险、回滚方式。
